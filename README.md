# Шифр-связь — локальный мессенджер

Мессенджер для устройств в одной локальной сети. Сервер устанавливается
на одном компьютере; Next.js-интерфейс лежит в соседней папке `project_front`.
Облачные сервисы, внешние аккаунты и интернет во время работы не нужны.

**Это MVP без сквозного шифрования.** TLS защищает соединение устройства с API,
но API и Rust-брокер обрабатывают текст сообщений. Название проекта не означает E2EE.

## Архитектура

```text
Браузеры устройств в LAN
           │ HTTPS + WSS, порт 8443
           ▼
 Nginx + Next.js UI ────── ../project_front
           │ /api/*, /ws (HTTPS + WSS)
           ▼
 Rust / Axum          ───── PostgreSQL 17: аккаунты, история, документы и аудит
           │ JSON/TCP, отдельное соединение на пользователя
           ▼
     Rust / Tokio :7000
   комнаты и личные сообщения
```

Собственный **shifr-broker** на Rust/Tokio маршрутизирует личные сообщения и
рассылки в комнаты. API проверяет права, сохраняет сообщение в PostgreSQL и передаёт
брокеру для доставки всем получателям с одним ID. Брокер сериализует событие один
раз и разделяет буфер между очередями получателей; медленные клиенты отключаются.
Протокол, лимиты, замеры и обновление: [Rust-брокер](docs/broker.md).

## Уже реализовано

- Закрытые аккаунты: создание через админ-панель, роли, отделы, блокировка и сброс пароля.
- История сообщений в PostgreSQL и обмен документами до 10 МиБ.
- Чаты отделов, объявления с записью для модераторов и полезные ресурсы.
- Журнал аудита входов, изменений аккаунтов и операций с документами.
- Локальная PostgreSQL: пароли с солью и scrypt, сессии со случайными токенами;
  в базе хранятся хеши токенов. Cookie: HttpOnly, SameSite=Strict, Secure при TLS.
- Комнаты: вход, выход, список участников, события присутствия.
- Личные сообщения онлайн-пользователям, серверное эхо отправителю, время сервера.
- HTTPS/WSS, генерация локального CA и сертификата для IP сервера.
- Проверка Origin, ограничение HTTP/WS-запросов, размера сообщений и очередей.
- Завершение соединений при выходе, истечении сессии и потере брокера.
- Health endpoints, Docker Compose и тесты с настоящим Rust-брокером.
- Next.js UI: вход, управление аккаунтами, чаты, личные диалоги, участники,
  непрочитанные сообщения, черновики в памяти вкладки и переподключение.

## Запуск в Linux без Docker

Из `project_back` выполните от обычного пользователя, подставив LAN-IP этого сервера:

```bash
./start-linux.sh 192.168.1.10
```

Скрипт собирает проект и запускает PostgreSQL, брокер, API и Nginx как службы
`systemd --user`. Откройте `https://192.168.1.10:8443`. Для первого входа выполните
`./start-linux.sh admin`. Следующий запуск — `./start-linux.sh`, остановка —
`systemctl --user stop shifr.target`. [Зависимости, автозапуск и перенос данных](docs/linux.md).

## Запуск в локальной сети через Docker Compose

На сервере нужен только **Docker с Compose v2** (Docker Desktop на macOS/Windows
или Docker Engine на Linux). Для `start.sh` на Windows используйте WSL.
API и брокер работают на Rust. Установщик и сборка Next.js используют Node.js внутри контейнеров.
Закрепите за сервером локальный IPv4 в DHCP, например `192.168.1.10`.

Папки должны лежать рядом:

```text
Documents/
├── project_back/    # API, Rust-брокер, общая конфигурация Compose
└── project_front/   # Next.js, Nginx, команда запуска
```

```bash
# Из project_back или project_front. Замените IP на адрес своего сервера.
./start.sh 192.168.1.10
```

Первый запуск собирает отдельный контейнер настройки, создаёт в `project_back`
`.env`, `runtime/` и `data/`, генерирует секреты и сертификаты, затем собирает и
поднимает `postgres`, `broker`, `api` и `web`. Скрипт ждёт healthcheck всех сервисов. Секреты
не выводятся в терминал. Повторный запуск `./start.sh` сохраняет настройку и аккаунты.
Если `.env` уже создан на этапе бэкенда, повторная генерация не нужна.

Откройте **`https://192.168.1.10:8443`**. UI, API и WebSocket работают по одному
адресу. Конфигурация не требует ручного задания URL бэкенда в браузере.

Не копируйте `.env.example` как готовый `.env`: в нём нет рабочих секретов.
Первая сборка требует интернет для загрузки образов и зависимостей.

Установите **`runtime/tls/ca.crt`** как доверенный локальный CA на устройствах,
которые будут подключаться. На iOS после установки профиля нужно отдельно
включить доверие сертификату. Все файлы `.key` остаются у администратора сервера;
в контейнер API попадает только серверный ключ, ключ CA хранится в `runtime/ca/`.
Серверный сертификат действует 365 дней и содержит указанный IP и `localhost`.

Для эксплуатации: [руководство SRE по выдаче, установке и продлению сертификатов](docs/certificates-sre.md).

Проверка с сервера, без отключения проверки TLS:

```bash
curl --cacert runtime/tls/ca.crt https://192.168.1.10:8443/health/ready
docker compose ps
```

Ожидаемый ответ: `{"status":"ok","broker":true}`. Остановить: `docker compose down`.
Данные PostgreSQL сохраняются в именованном томе `pgdata` после `docker compose down`.
Команда `docker compose down -v` удаляет том. Для резервной копии используйте
`pg_dump`. [Копирование и восстановление](docs/organization.md#аудит-и-резервные-копии).

**Обновление с SQLite.** Перед обновлением остановите прежние `web` и `api` и
сохраните копию `data/`, `.env` и `runtime/`. Затем выполните `./start.sh` из
обновлённого проекта. API перенесёт содержимое `data/shifr.sqlite` в пустую PostgreSQL
один раз. [Порядок переноса](docs/organization.md#обновление-существующей-установки).

Публичная регистрация закрыта. Для первого входа создайте администратора
командой на сервере, затем выдавайте аккаунты через «Управление и аудит».
Пошаговая инструкция, матрица ролей, обновление существующей базы и резервное
копирование: **[эксплуатация организации](docs/organization.md)**.

## Смена адреса сервера

Когда сервер получил новый частный IPv4, из `project_back` выполните:

```bash
./change-ip.py 192.168.1.25
```

Подставьте новый адрес своего сетевого интерфейса. Команда обновит настройки и
серверный сертификат, а для работающего мессенджера проверит HTTPS по новому адресу.
На устройствах откройте новый URL. Установленный CA продолжит работать. Если на
хосте есть обе установки, добавьте `--native` или `--compose`.
[Подробности и откат](docs/certificates-sre.md#6-продление-сертификата-или-смена-lan-ip).

## Граница LAN и работа без интернета

Compose публикует только Nginx на `LAN_IP:8443`; порты API и брокера не публикуются.
PostgreSQL, API и Rust-брокер находятся во внутренней Docker-сети. Для Nginx есть отдельный bridge,
позволяющий отвечать устройствам LAN. Статика, иконки и шрифты не требуют внешних
сервисов; Next.js экспортируется в статические файлы, телеметрия при сборке отключена.
Nginx проверяет сертификат API по локальному CA и перезаписывает `X-Forwarded-For`.
API доверяет одному локальному прокси только в Compose (`TRUST_PROXY=1`), чтобы
лимиты запросов применялись к реальным IP клиентов. При прямом запуске доверие выключено.

На хосте разрешите входящий TCP 8443 только из своей подсети. Не создавайте
проброс порта на роутере или публичный туннель: привязка к LAN-IP и проверка IP
не заменяют firewall, особенно если NAT скрывает исходный адрес клиента.
Для полного запрета исходящего трафика Nginx задайте правило firewall хоста.

Для изолированного стенда заранее соберите автономный пакет на машине той же
архитектуры с интернетом:

```bash
bash scripts/export-offline.sh /absolute/path/to/shifr-offline
```

Перенесите каталог на сервер с Docker и Compose v2; из него выполните
`sudo bash start.sh <LAN-IP>`. Пакет содержит образы, Compose и инструкции,
не включает секреты и данные текущей установки. При запуске используются
`--no-build --pull never`. Подробности — в [инструкции](docs/organization.md#пакет-для-изолированной-сети).

## Интерфейс Next.js

Код и инструкция: [../project_front/README.md](../project_front/README.md).
Контракт HTTP и WebSocket: [docs/api.md](docs/api.md). В Compose интерфейс обращается
к относительным `/api/*` и `/ws`; `ALLOWED_ORIGINS` содержит адрес `https://LAN-IP:8443`.
Для отдельной разработки Next.js на порту 3000 задайте `NEXT_PUBLIC_API_URL`:
имя/IP и схема HTTPS должны совпадать с API. Смешивание `localhost` и IP нарушает cookie.

В браузерном клиенте:

```ts
const api = 'https://192.168.1.10:8443';
const response = await fetch(`${api}/api/auth/login`, {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ nickname, password }),
});
if (!response.ok) throw new Error('Не удалось войти');

const socket = new WebSocket(`${api.replace('https:', 'wss:')}/ws`);
socket.addEventListener('message', ({ data }) => {
  const event = JSON.parse(data);
  if (event.type === 'ready') {
    socket.send(JSON.stringify({ type: 'join', channel: '#general' }));
  }
  // Обновить состояние UI; текст сообщения выводить обычным текстом.
});
```

Cookie отправляется браузером автоматически; токены в query string или
localStorage не нужны. В этой версии один аккаунт может иметь только одно
активное соединение чата, включая вкладки. UI должен дождаться `ready`, а после
переподключения заново войти в нужные комнаты. Отправленные сообщения показываются
по серверному событию `message`; получение события не означает прочтение адресатом.

## Разработка и проверки

API и WebSocket-шлюз собираются из `api/` (Rust, Axum, Tokio). API использует пул
соединений с PostgreSQL. Сервис `broker` отвечает за рассылку.

Для локальной сборки нужны Rust 1.91.1, компилятор C и OpenSSL 3 с заголовками
(на Debian / Ubuntu — `build-essential pkg-config libssl-dev`). Из корня проекта:

```bash
cargo build --release --locked --manifest-path api/Cargo.toml
cargo build --release --locked --manifest-path broker/Cargo.toml
```

Для ручной разработки API без systemd подготовьте локальную PostgreSQL 17, базу и роль-владельца.
Экспортируйте параметры из созданного установщиком файла `.env`
в двух терминалах (`set -a; . ./.env; set +a`). Для API задайте `PGHOST`, `PGPORT`, `PGDATABASE`,
`PGUSER` и `PGPASSWORD` для своей БД либо `DATABASE_URL`. Для импорта старой базы
вне Compose экспортируйте также `LEGACY_SQLITE_PATH` с путём к файлу SQLite.
В первом терминале выполните `broker/target/release/shifr-broker`,
во втором — `api/target/release/shifr-api`.

Тесты на Node.js 24 запускают отдельную PostgreSQL 17 через Docker, Rust API и брокер.
Проверки миграции создают временные файлы SQLite старого формата. Для проверки TLS требуется OpenSSL в PATH.

```bash
npm ci
npm run check
cargo test --manifest-path broker/Cargo.toml --locked
```

Для проверки с локальным Nginx соберите фронтенд и выполните
`NGINX_BINARY=/path/to/nginx npm run test:stack`.
[Замер производительности брокера](docs/broker.md#производительность) относится к маршрутизации.

## Ограничения

- Нет E2EE: сервер видит текст. TCP между API и брокером идёт во внутренней сети
  одного хоста; не переносите его на другой хост без защиты канала.
- Личные сообщения отправляются онлайн-получателям; очереди офлайн-доставки нет.
- История, документы и аудит сохраняются без автоматической ротации. Нужны
  контроль диска и защищённые резервные копии. Аудит не защищён от изменений владельцем хоста.
- Один отдел на сотрудника; администратор видит все отделы, чужие личные диалоги
  через API недоступны. Новый член отдела видит всю его историю.
- 10 МиБ на файл, 1 ГиБ суммарно на содержимое файлов. Антивирусной проверки нет.
- Один экземпляр API с PostgreSQL, одно активное подключение чата на аккаунт,
  до 20 комнат на подключение, 512 участников онлайн в комнате, 4096 TCP-соединений
  брокера. Эти ограничения не являются гарантией пропускной способности всего приложения.
- Нет автоматического обновления сертификатов, самостоятельного восстановления
  пароля и подтверждения прочтения.
