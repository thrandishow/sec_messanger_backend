# Шифр-связь — локальный мессенджер

Мессенджер для устройств в одной локальной сети. Сервер устанавливается
на одном компьютере; Next.js-интерфейс лежит в соседней папке `project_front`.
Облачные сервисы, внешние аккаунты и интернет во время работы не нужны.

**Это MVP без сквозного шифрования.** TLS защищает соединение устройства с API,
но API и InspIRCd обрабатывают текст сообщений. Название проекта не означает E2EE.

## Архитектура

```text
Браузеры устройств в LAN
           │ HTTPS + WSS, порт 8443
           ▼
 Nginx + Next.js UI ────── ../project_front
           │ /api/*, /ws (HTTPS + WSS)
           ▼
 TypeScript / Fastify ───── SQLite: пользователи и сессии
           │ IRC, отдельное соединение на пользователя
           ▼
     InspIRCd 4.12.1
   комнаты и личные сообщения
```

[InspIRCd](https://github.com/inspircd/inspircd) действительно маршрутизирует
сообщения, управляет участниками и каналами. API преобразует JSON в ограниченный
набор IRC-команд. Используется стабильный релиз `v4.12.1`, а не `master`;
Dockerfile собирает его из исходников и проверяет SHA-256 архива.

## Уже реализовано

- Регистрация по общему коду приглашения, вход, выход и проверка сессии.
- Локальная SQLite: пароли с солью и scrypt, сессии со случайными токенами;
  в базе хранятся хеши токенов. Cookie: HttpOnly, SameSite=Strict, Secure при TLS.
- Комнаты: вход, выход, список участников, события присутствия.
- Личные сообщения онлайн-пользователям, серверное эхо отправителю, время сервера.
- HTTPS/WSS, генерация локального CA и сертификата для IP сервера.
- Проверка Origin, ограничение HTTP/WS-запросов, размера сообщений и очередей.
- Завершение соединений при выходе, истечении сессии и потере IRC.
- Health endpoints, Docker Compose и тесты с настоящим InspIRCd.
- Next.js UI: вход и регистрация, комнаты, личные диалоги, участники,
  непрочитанные сообщения, черновики в памяти вкладки и переподключение.

## Запуск в локальной сети

На сервере нужен только **Docker с Compose v2** (Docker Desktop на macOS/Windows
или Docker Engine на Linux). Для `start.sh` на Windows используйте WSL.
Node.js и OpenSSL выполняются внутри контейнеров.
Закрепите за сервером локальный IPv4 в DHCP, например `192.168.1.10`.

Папки должны лежать рядом:

```text
Documents/
├── project_back/    # API, InspIRCd, общая конфигурация Compose
└── project_front/   # Next.js, Nginx, команда запуска
```

```bash
# Из project_back или project_front. Замените IP на адрес своего сервера.
./start.sh 192.168.1.10
```

Первый запуск собирает отдельный контейнер настройки, создаёт в `project_back`
`.env`, `runtime/` и `data/`, генерирует секреты и сертификаты, затем собирает и
поднимает `inspircd`, `api`, `web`. Скрипт ждёт healthcheck всех сервисов. Секреты
не выводятся в терминал. Повторный запуск `./start.sh` сохраняет настройку и аккаунты.
Если `.env` уже создан на этапе бэкенда, повторная генерация не нужна.

Откройте **`https://192.168.1.10:8443`**. UI, API и WebSocket работают по одному
адресу. Конфигурация не требует ручного задания URL бэкенда в браузере.

Не копируйте `.env.example` как готовый `.env`: в нём нет рабочих секретов.
Первая сборка требует интернет для загрузки образов и зависимостей.

Установите **`runtime/tls/ca.crt`** как доверенный локальный CA на устройствах,
которые будут подключаться. На iOS после установки профиля нужно отдельно
включить доверие сертификату. Все файлы `.key` остаются у администратора сервера;
в контейнер API попадает только серверный ключ, ключ CA хранится в `runtime/ca/`.
Серверный сертификат действует 365 дней и содержит указанный IP и `localhost`.

Для эксплуатации: [руководство SRE по выдаче, установке и продлению сертификатов](docs/certificates-sre.md).

Проверка с сервера, без отключения проверки TLS:

```bash
curl --cacert runtime/tls/ca.crt https://192.168.1.10:8443/health/ready
docker compose ps
```

Ожидаемый ответ: `{"status":"ok","irc":true}`. Остановить: `docker compose down`.
Каталог `data/` при этом сохраняется. Перед резервным копированием SQLite остановите
API (`docker compose stop api`), скопируйте весь `data/`, затем запустите его снова.

Код для регистрации — `REGISTRATION_TOKEN` в локальном `.env`. Администратор
передаёт его разрешённым пользователям; **не помещайте его в `NEXT_PUBLIC_*`**
и не зашивайте в UI. Для отзыва старого приглашения замените только этот параметр
случайной строкой из 64 hex-символов и пересоздайте API. Аккаунты сохранятся.

## Граница LAN и работа без интернета

Compose публикует только Nginx на `LAN_IP:8443`; порты API и IRC не публикуются.
API и InspIRCd находятся во внутренней Docker-сети. Для Nginx есть отдельный bridge,
позволяющий отвечать устройствам LAN. Статика, иконки и шрифты не требуют внешних
сервисов; Next.js экспортируется в статические файлы, телеметрия при сборке отключена.
Nginx проверяет сертификат API по локальному CA и перезаписывает `X-Forwarded-For`.
API доверяет одному локальному прокси только в Compose (`TRUST_PROXY=1`), чтобы
лимиты запросов применялись к реальным IP клиентов. При прямом запуске доверие выключено.

На хосте разрешите входящий TCP 8443 только из своей подсети. Не создавайте
проброс порта на роутере или публичный туннель: привязка к LAN-IP и проверка IP
не заменяют firewall, особенно если NAT скрывает исходный адрес клиента.
Для полного запрета исходящего трафика Nginx задайте правило firewall хоста.

Первичная сборка скачивает исходники, npm-пакеты и базовые Docker-образы.
Для изолированной сети можно заранее собрать образы на машине той же архитектуры:

```bash
docker compose build
docker compose -f compose.setup.yaml build
docker save -o shifr-images.tar shifr-svyaz-api:0.1.0 shifr-svyaz-inspircd:4.12.1 shifr-svyaz-web:0.1.0 shifr-svyaz-setup:0.1.0
```

На изолированном сервере перенесите обе папки проекта и архив образов. Для первого
старта из `project_back` выполните (IP замените на адрес изолированного сервера):

```bash
docker load -i shifr-images.tar
docker compose -f compose.setup.yaml run --rm --no-build --pull never --user "$(id -u):$(id -g)" setup --ip 192.168.1.10
docker compose up -d --no-build --pull never
```

## Интерфейс Next.js

Код и инструкция: [../project_front/README.md](../project_front/README.md).
Контракт HTTP и WebSocket: [docs/api.md](docs/api.md). В Compose интерфейс обращается
к относительным `/api/*` и `/ws`; `ALLOWED_ORIGINS` содержит адрес `https://LAN-IP:8443`.
Для отдельной разработки Next.js на порту 3000 задайте `NEXT_PUBLIC_API_URL`:
имя/IP и схема HTTPS должны совпадать с API. Смешивание `localhost` и IP нарушает cookie.

В браузерном клиенте:

```ts
const api = 'https://192.168.1.10:8443';
const response = await fetch(`${api}/api/auth/login`, {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ nickname, password }),
});
if (!response.ok) throw new Error('Не удалось войти');

const socket = new WebSocket(`${api.replace('https:', 'wss:')}/ws`);
socket.addEventListener('message', ({ data }) => {
  const event = JSON.parse(data);
  if (event.type === 'ready') {
    socket.send(JSON.stringify({ type: 'join', channel: '#general' }));
  }
  // Обновить состояние UI; текст сообщения выводить обычным текстом.
});
```

Cookie отправляется браузером автоматически; токены в query string или
localStorage не нужны. В этой версии один аккаунт может иметь только одно
активное соединение чата, включая вкладки. UI должен дождаться `ready`, а после
переподключения заново войти в нужные комнаты. Отправленные сообщения показываются
по серверному событию `message`; получение события не означает прочтение адресатом.

## Разработка и проверки

```bash
npm ci
npm run check            # TypeScript, unit/API/setup tests, production build
npm run dev              # .env + локальный InspIRCd на 127.0.0.1:6667
```

`npm run dev` сам не запускает IRC. Для разработки без Docker соберите
[InspIRCd 4.12.1 по официальной инструкции](https://docs.inspircd.org/4/installation/source/),
возьмите `docker/inspircd/inspircd.conf`, замените адрес listener на `127.0.0.1`,
а путь include — на абсолютный путь к `runtime/irc-connect.conf` этого проекта.
Запускайте с `--nofork --nopid --nolog --config <путь-к-конфигу>`.

Интеграционный тест самостоятельно запускает отдельный InspIRCd, API и двух WSS-клиентов
на временных loopback-портах, использует временную SQLite и завершает процессы:

```bash
INSPIRCD_BINARY=/absolute/path/to/inspircd/bin/inspircd npm run test:integration
```

Он проверяет сертификаты, регистрацию, защиту WSS, комнаты, Unicode-сообщения,
серверное эхо, личные сообщения, список участников, выход, истечение сессии и
остановку IRC. Отсутствующий бинарник — ошибка, а не пропуск теста.

Для проверки всей цепочки через Nginx сначала соберите фронтенд (`npm ci && npm run build`
в `project_front`), затем выполните:

```bash
INSPIRCD_BINARY=/path/to/inspircd NGINX_BINARY=/path/to/nginx npm run test:stack
```

Проверено при реализации: обе production-сборки, 11 тестов бэкенда, 6 тестов
состояния UI, отдача Next.js-страницы и JS-файлов через Nginx, HTTPS API и WSS
с настоящим InspIRCd 4.12.1. Проверены приглашение, сессии, комнаты, личные сообщения,
список участников, выход, истечение сессии и остановка IRC.

Docker-образы и подключение двух физических устройств ещё не проверены: в среде
разработки нет Docker. Браузерная визуальная проверка также недоступна в этой сессии.

## Ограничения первого этапа

- Нет E2EE: сервер видит текст. IRC между контейнерами идёт по внутренней сети
  одного хоста без TLS; не переносите IRC на другой компьютер без защиты этого канала.
- История сообщений, офлайн-доставка и вложения пока отсутствуют. Переписка не
  записывается в SQLite или прикладные логи. Это не гарантия отсутствия текста
  в памяти, swap, дампах процесса или сторонней диагностике хоста.
- Комната существует, пока в ней есть участники. Публичные комнаты доступны
  всем зарегистрированным пользователям, личное сообщение — конкретному нику.
- Ники: 3–24 латинских символа, цифры и `_`, первая буква; хранятся в нижнем регистре.
  Комнаты: `#` + 1–48 строчных латинских символов, цифр, `_` или `-`.
  Сообщение: до 350 байт UTF-8, одна строка.
- Нет восстановления пароля, админ-панели, поддержки нескольких устройств одновременно и автоматического
  обновления сертификатов. SQLite рассчитана на один экземпляр API.

E2EE нужно спроектировать совместно с клиентом, включая ключи устройств,
проверку собеседника и восстановление.
