# Rust-брокер сообщений

`shifr-broker` заменяет InspIRCd. Это маршрутизатор для протокола проекта:
комнаты, личные сообщения, списки участников и события присутствия.
Совместимости с IRC-клиентами нет. Браузерный HTTP/WSS API v2 сохраняется.

## Запуск и обновление

Из `project_back`, при уже настроенной установке:

```bash
./start.sh
```

На Linux при необходимости: `sudo ./start.sh`. На новом сервере передайте
LAN-IP: `./start.sh 192.168.1.10`. Нужен Docker с Compose v2; Rust и Node.js
компилируются внутри контейнеров. Первая сборка требует интернет.

Для перехода со старой версии сначала сделайте резервную копию по
[инструкции эксплуатации](organization.md). Обновите backend и соседний
`project_front`. `start.sh` пересобирает сервисы и использует `--remove-orphans`,
поэтому старый контейнер InspIRCd удаляется. На время обновления чат отключится.
Аккаунты, история, файлы, `.env` и сертификаты сохраняются; новый CA не нужен.

Старая переменная `IRC_PASSWORD` принимается как секрет брокера, если нет
`BROKER_TOKEN`. Compose сам задаёт API адрес `broker:7000`, поэтому старые
`IRC_HOST`/`IRC_PORT` игнорируются. `runtime/irc-connect.conf` больше не читается;
его наличие не мешает запуску. Новый setup создаёт только `BROKER_TOKEN`.
Для явной миграции названия переменной перенесите старое значение в
`BROKER_TOKEN`, не выводя его в терминал. Перезапустите API и брокер вместе.

Офлайн-пакет теперь содержит `shifr-svyaz-broker:0.1.0` вместо InspIRCd.
Порядок обновления образов, конфигурации и базы описан в
[инструкции для изолированной сети](organization.md#пакет-для-изолированной-сети).

## Ответственность компонентов

- API: аккаунты, сессии, роли, отделы, доступ к чатам и файлам, PostgreSQL, аудит.
- Rust: активные подключения, комнаты, присутствие и рассылка сообщений.
- Nginx: HTTPS/WSS для браузеров и проверенный HTTPS/WSS до API.

API открывает одно TCP-соединение на подключённого пользователя. Секрет
аутентифицирует доверенный API; брокер не проверяет пользовательские пароли
и организационные роли. Он проверяет уникальность ника и членство в комнате.
Не публикуйте порт 7000 и не выдавайте секрет клиентским устройствам.
В Compose брокер находится только во внутренней сети, без опубликованных портов.
TCP между API и брокером не шифруется: поддерживается размещение на одном хосте.
Сквозного шифрования нет; API и брокер видят текст сообщений.

## Сохранение и доставка

1. API проверяет сессию, права и вложение, отправляет `prepare` с уникальным requestId.
2. Брокер проверяет членство в комнате или наличие личного адресата онлайн и
   возвращает `accepted`. На этом этапе сообщение не рассылается.
3. API записывает сообщение в PostgreSQL один раз и получает ID, время и метаданные файла.
4. API отправляет `publish`. Брокер проверяет requestId, автора, адресата и ID,
   затем рассылает одно сохранённое событие участникам и отправителю.

При ошибке PostgreSQL API отменяет подготовку (`cancel`). Один отправитель может
иметь одну незавершённую отправку. API запрещает менять членство до подтверждения.
Брокер отклоняет повторный commit без подготовки и ID, не возрастающий в рамках
текущего соединения. Повтор запроса из браузера после reconnect не идемпотентен.

Событие `message` у отправителя подтверждает сохранение и обработку брокером,
но не получение или прочтение всеми адресатами. Если получатель отключится после
`accepted`, сообщение всё равно может сохраниться. Если API/брокер упадёт между
commit PostgreSQL и рассылкой, сообщение останется в истории, а live-событие потеряется.
После reconnect повторите join и загрузите history, объединяя сообщения по ID.
При таймауте проверьте историю перед ручной повторной отправкой.

Брокер не хранит сообщения на диске и не воспроизводит их после рестарта.
Это не распределённая очередь и не замена Kafka/NATS. Приложение рассчитано
на один API с PostgreSQL; кластера, репликации и очереди офлайн-доставки нет.

## Внутренний протокол v1

UTF-8 JSON, одно событие на строку, разделитель LF. Первый кадр за 5 секунд:

```json
{"type":"hello","version":1,"token":"<64 hex characters>","nickname":"alice"}
```

После `ready` доступны `join`, `part`, `names`, `ping`, `prepare`, `publish`,
`cancel`. Пример последовательности (ID выдаёт PostgreSQL, а не клиент):

```json
{"type":"prepare","requestId":"unique-request-1","target":"#general"}
{"type":"accepted","requestId":"unique-request-1","target":"#general"}
{"type":"publish","requestId":"unique-request-1","message":{"id":42,"from":"alice","target":"#general","text":"Привет","time":"2026-11-19T12:00:00.000Z"}}
```

`accepted` — ответ брокера. События для браузера: ready, join, part, quit,
names, message, pong, error. Файл не проходит через брокер: только
`attachment: {id,name,size}`. Ники/комнаты — ASCII в нижнем регистре.
Ошибки prepare/publish содержат requestId; ошибка другой команды не отменяет
текущую отправку. Неизвестные команды и поля отклоняются; некорректный JSON закрывает соединение.
Коды ошибок и клиентский контракт: [API](api.md).

## Лимиты и защита от перегрузки

| Ограничение | Значение |
| --- | --- |
| TCP-соединения, включая healthcheck/handshake | 4096 |
| Комнаты на пользователя | 20 |
| Онлайн-участники комнаты | 512 |
| Входящий кадр с LF | 4096 байт |
| Текст сообщения | 350 байт UTF-8 |
| Очередь получателя | 128 событий, максимум 256 КиБ с учётом записи |
| Очередь команд маршрутизатора | 4096 |
| Таймаут записи TCP | 5 секунд |
| Неактивность клиента брокера | 90 секунд; API ping раз в 25 секунд |
| Ожидание отправки в API | 10 секунд, затем закрытие WSS |

Tokio обслуживает сокеты асинхронно. Один обработчик последовательно меняет
состояние комнат; он не ждёт записи в сокет и не держит глобальный mutex во время
I/O. JSON события сериализуется один раз в `Arc<[u8]>`; очереди получателей
разделяют эти байты. TCP_NODELAY выключает задержку Нейгла.
При переполнении очереди медленный клиент отключается; остальные продолжают работу.
Очередь входящих команд ограничена и применяет обратное давление к чтению сокетов.
Это пределы ресурсов, а не обещание обслуживания 4096 пользователей под любой нагрузкой.

## Эксплуатация

```bash
docker compose ps
docker compose logs --tail=80 postgres broker api web
docker compose exec broker shifr-broker healthcheck
curl --cacert runtime/tls/ca.crt https://192.168.1.10:8443/health/ready
```

Ожидается `{"status":"ok","broker":true}`. При недоступности брокера API
возвращает HTTP 503 и закрывает активные WSS-соединения. Healthcheck проверяет
секрет и ответ обработчика маршрутизации, а не только доступность TCP-порта.
При достижении лимита соединений healthcheck тоже может отказать.
После рестарта клиент переподключается и повторяет join; история остаётся в PostgreSQL.
Брокер не пишет токены, тексты сообщений или содержимое кадров в логи.

Переменные: `BROKER_TOKEN` (64 hex-символа), `BROKER_BIND` (для бинарника,
по умолчанию `127.0.0.1:7000`); `BROKER_HOST`/`BROKER_PORT` — для API.
В Compose bind равен `0.0.0.0:7000` внутри приватной сети.
Права на `.env` и резервные копии сохраняйте закрытыми.

## Производительность

В репозитории есть отдельный генератор `broker/examples/benchmark.rs`.
Он запускает release-брокер отдельным процессом и использует настоящие TCP-сокеты
на loopback. В каждой группе один отправитель и несколько получателей.
Каждая отправка проходит prepare → accepted → publish → echo. Генератор проверяет
ID и порядок у каждого получателя, измеряет время от начала prepare до получения
message. Подключения создаются до замера. Отдельного прогрева нет.

```bash
cargo build --release --locked --manifest-path broker/Cargo.toml
cargo build --release --locked --example benchmark --manifest-path broker/Cargo.toml
BROKER_BINARY="$PWD/broker/target/release/shifr-broker" \
  broker/target/release/examples/benchmark 4 8 50000
```

Аргументы: количество групп, получателей в группе, сообщений от каждого отправителя.
Вывод — JSON с числом сообщений/доставок в секунду и p50/p95/p99 задержки.
Генератор использует только синтетические данные и отдельный тестовый секрет;
рабочие `.env`, БД и сертификаты не читает.

Замер 19.11.2026: Apple M3 Pro, 36 ГиБ RAM, macOS 26.6.2 arm64, Rust 1.91.1,
release + thin LTO. 4 отправителя, по 8 получателей (36 подключений), текст 128 байт.
200 000 сообщений, 1 600 000 проверенных доставок за 6,252 секунды:

| Метрика | Результат одного прогона |
| --- | --- |
| Сообщения/с | 31 991 |
| Доставки/с, без эха отправителю | 255 928 |
| Задержка p50 | 0,118 мс |
| Задержка p95 | 0,176 мс |
| Задержка p99 | 0,219 мс |

Это тест **брокера вместе с генератором на одном компьютере**. PostgreSQL, API,
TLS, браузер и физическая LAN в измерение не входят. Скорость всего мессенджера
будет ниже; запись в PostgreSQL и проверки API могут стать пределом.
Результат не является SLA, пределом масштабирования или сравнением с InspIRCd/Go.

## Проверки

```bash
cargo test --locked --manifest-path broker/Cargo.toml
cargo clippy --locked --all-targets --manifest-path broker/Cargo.toml -- -D warnings
npm run check
```

Rust-тесты проверяют framing, переполнение очередей, авторизацию, уникальность ника,
двухэтапную отправку, повторный commit, порядок, членство, вложения и освобождение
ника при обрыве. Интеграционные тесты используют реальный брокер, HTTPS и WSS.
