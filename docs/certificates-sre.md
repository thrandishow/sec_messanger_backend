# Шифр-связь: сертификаты — руководство для SRE

## 1. Что выдаём пользователям

На клиентском устройстве не нужно выпускать отдельный сертификат. Администратор
передаёт **только `runtime/tls/ca.crt`** и устанавливает его как доверенный корневой
центр сертификации (CA). После этого браузер доверяет серверному сертификату.

Клиентских сертификатов и mTLS в текущей реализации нет. Пользователь входит
по логину и паролю из админ-панели; создание аккаунта не связано с сертификатами.
TLS защищает транспорт, но не обеспечивает сквозное шифрование сообщений.

| Файл относительно `project_back` | Назначение | Куда передавать |
| --- | --- | --- |
| `runtime/tls/ca.crt` | Публичный корневой сертификат; срок при создании — 3650 дней | На разрешённые клиентские устройства |
| `runtime/ca/ca.key` | Закрытый ключ CA, подписывает серверные сертификаты | Только защищённое хранение у SRE; не клиентам и не в контейнеры приложения |
| `runtime/tls/server.crt` | Серверный сертификат; срок при создании — 365 дней | Nginx и API через Docker bind mount |
| `runtime/tls/server.key` | Закрытый ключ сервера | Только сервер и защищённые резервные копии |

Нельзя передавать пользователям весь `runtime/`, `.env` или файлы `.key`.
Сертификат CA не секретен, но его подлинность необходимо проверить: установка
чужого CA даёт ему возможность подписывать сертификаты, которым будет доверять устройство.

## 2. Условия и архитектура

Команды ниже предназначены для **Linux, Bash**, из каталога `project_back`.
Нужны Docker Engine, Compose v2; для ручного перевыпуска — **OpenSSL 3**, `curl`
и стандартные утилиты Linux. Первичная настройка выполняет OpenSSL внутри Docker.
Папка `project_front` должна лежать рядом с `project_back`.

В примерах используется `192.168.1.10`. Замените его на реальный постоянный IPv4
сервера из локальной сети. Закрепите адрес в DHCP или настройте статический адрес.
Проверьте интерфейсы командой `ip -4 addr show`: адрес Docker bridge не подходит.

```text
Браузер → HTTPS/WSS → Nginx:8443 → HTTPS/WSS → API → IRC → InspIRCd
           доверие к CA           доверие к тому же CA
```

Nginx и API используют одну пару `server.crt` / `server.key`.
В `project_front/nginx.conf` настроены `proxy_ssl_verify on` и
`proxy_ssl_name localhost`. Поэтому сертификат обязательно должен содержать
**`DNS:localhost`** даже при входе пользователей по IP.
Для входа по IP нужен **IP SAN**, одного `CN` недостаточно.

Compose публикует только `${LAN_IP}:8443`. Значение `LAN_IP` должно принадлежать
сетевому интерфейсу хоста. Доступ через другой IP или DNS требует соответствующего
SAN и записи в `ALLOWED_ORIGINS`; ниже описан штатный вариант с одним LAN-IP.

## 3. Первый выпуск на новом сервере

Выполняйте из обычной учётной записи владельца проекта, **не из root-shell**.
Пользователь должен иметь право записи в `project_back`.
Если Docker доступен без `sudo`, достаточно:

```bash
bash start.sh 192.168.1.10
```

Если Docker требует `sudo`, используйте явный запуск настройки:

```bash
sudo docker compose -f compose.setup.yaml build
sudo docker compose -f compose.setup.yaml run --rm \
  --user "$(id -u):$(id -g)" setup --ip 192.168.1.10
sudo docker compose up --build -d --wait --wait-timeout 180
```

Здесь `id` выполняется обычным пользователем до вызова `sudo`: файлы будут
принадлежать ему. Обновлённый `start.sh` также учитывает `SUDO_UID`/`SUDO_GID`.
В прежней версии запуск через sudo мог оставлять файлы у root при UID 1000
в контейнерах; для таких установок см. исправление владельцев в разделе 8.

Setup создаёт CA, серверную пару, `.env`, IRC-конфигурацию и каталог данных.
Он отказывается перезаписывать существующие `.env` или `runtime/`.
Для действующего сервера используйте раздел перевыпуска; не удаляйте конфигурацию
ради повторного запуска setup.

## 4. Проверка и передача CA

На сервере выведите публичные метаданные и SHA-256 fingerprint:

```bash
openssl x509 -in runtime/tls/ca.crt -noout \
  -subject -issuer -dates -fingerprint -sha256
```

Передайте `ca.crt` через доверенный канал: управляемую доставку MDM/GPO,
SCP с проверенным ключом сервера или физический носитель.
Fingerprint сообщите независимо от канала доставки файла. Получатель сверяет
его до установки. На машине с OpenSSL используется та же команда; в Windows —
`certutil -hashfile ca.crt SHA256` сравнивает хеш файла, **не fingerprint сертификата**.
Для такого способа заранее вычислите на сервере именно `sha256sum runtime/tls/ca.crt`.

В журнале выдачи фиксируйте владельца/устройство, дату, fingerprint CA и результат
проверки подключения. Закрытые ключи и код приглашения в журнал не включайте.

## 5. Установка на устройствах

### Windows

Откройте `ca.crt` → «Установить сертификат» → «Текущий пользователь» →
«Поместить все сертификаты в следующее хранилище» →
«Доверенные корневые центры сертификации». Проверьте выбранный CA и завершите импорт.

Для всех пользователей компьютера используйте хранилище локального компьютера
с правами администратора. Для парка устройств предпочтительна доставка через GPO/MDM.

### Ubuntu / Debian

Из папки с полученным файлом:

```bash
sudo install -m 0644 ca.crt /usr/local/share/ca-certificates/shifr-svyaz.crt
sudo update-ca-certificates
```

Другие дистрибутивы используют свои системные хранилища; эти команды относятся
к Ubuntu/Debian. Браузер может использовать отдельное хранилище.

### macOS

Откройте «Связка ключей», импортируйте `ca.crt` в подходящую связку («Система» —
для всех пользователей, с правами администратора). Откройте сертификат
`Shifr Svyaz Local CA` → «Доверие» → разрешите доверие для SSL.
Для управляемых компьютеров используйте профиль MDM.

### Android

Настройки → безопасность → шифрование и учётные данные → установить сертификат →
**сертификат ЦС**. Выберите `ca.crt`. Названия разделов зависят от производителя
и версии Android; устройство может потребовать PIN-код.

Пользовательский CA подходит не всем приложениям: приложение может игнорировать
это хранилище или использовать certificate pinning. Проверяйте именно браузер,
в котором открывается мессенджер. На управляемом устройстве используйте MDM.

### iPhone / iPad

Откройте переданный файл. В настройках установите загруженный профиль
(«Основные» → «VPN и управление устройством»; расположение зависит от версии iOS).
Затем «Основные» → «Об этом устройстве» → «Доверие сертификатам» → включите полное
доверие к `Shifr Svyaz Local CA`. Для ручной установки одного профиля недостаточно.
Для управляемых устройств правила доверия задаёт MDM.

### Firefox и отдельные хранилища браузеров

Если системного доверия недостаточно: настройки Firefox → «Приватность и защита» →
сертификаты → «Просмотр сертификатов» → «Центры сертификации» → «Импортировать».
Выберите `ca.crt` и разрешите доверять CA для идентификации веб-сайтов.
В управляемой среде используйте политики браузера.

### Приёмка устройства

Перезапустите браузер, подключитесь к LAN и откройте
`https://192.168.1.10:8443`. Проверьте отсутствие предупреждений TLS,
вход и отправку сообщения между двумя аккаунтами на разных устройствах.
Не используйте исключение безопасности браузера как признак успешной установки.

## 6. Продление сертификата или смена LAN-IP

При неизменном CA повторно устанавливать `ca.crt` на устройствах не нужно.
Перевыпускается серверный сертификат; ниже одновременно создаётся новый серверный
ключ. CA не меняется. При смене IP также обновляются `LAN_IP` и `ALLOWED_ORIGINS`.

Предусмотрите короткое окно обслуживания: перезапуск API/Nginx разорвёт WebSocket.
Ниже сохраняется InspIRCd; пользователи смогут переподключиться. Память браузера
не является долговременным хранилищем сообщений.

Выполняйте блоки последовательно **в одной Bash-сессии**, обычным владельцем
файлов проекта. При любой ошибке остановитесь, не переходите к установке.
Проверьте OpenSSL 3 (`openssl version`), фактический IP (`ip -4 addr show`),
срок CA и его доступность:

```bash
openssl x509 -in runtime/tls/ca.crt -noout -dates
openssl x509 -in runtime/tls/ca.crt -checkend 31536000 -noout
```

Код выхода последней команды должен быть 0: CA должен действовать дольше нового
сертификата (365 дней). Иначе сначала запланируйте замену CA, см. раздел 9.

### 6.1. Подготовка без изменения действующих файлов

Для продления укажите прежний IP, для переноса — новый:

```bash
set -euo pipefail
umask 077
SHIFR_IP=192.168.1.10
SHIFR_CERT_WORK=$(mktemp -d "$PWD/runtime/cert-renew.XXXXXX")
SHIFR_CERT_BACKUP=$(mktemp -d "$PWD/runtime/cert-backup.XXXXXX")
cp -p .env "$SHIFR_CERT_BACKUP/env"
cp -p runtime/tls/server.crt runtime/tls/server.key "$SHIFR_CERT_BACKUP/"

cat > "$SHIFR_CERT_WORK/server.ext" <<EOF
subjectAltName=IP:${SHIFR_IP},IP:127.0.0.1,DNS:localhost
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
EOF

openssl req -new -newkey rsa:3072 -noenc \
  -keyout "$SHIFR_CERT_WORK/server.key" \
  -out "$SHIFR_CERT_WORK/server.csr" -subj '/CN=Shifr Svyaz Local'
openssl x509 -req -in "$SHIFR_CERT_WORK/server.csr" \
  -CA runtime/tls/ca.crt -CAkey runtime/ca/ca.key \
  -set_serial "0x$(openssl rand -hex 16)" -days 365 -sha256 \
  -extfile "$SHIFR_CERT_WORK/server.ext" -out "$SHIFR_CERT_WORK/server.crt"

openssl verify -CAfile runtime/tls/ca.crt -purpose sslserver \
  -verify_ip "$SHIFR_IP" "$SHIFR_CERT_WORK/server.crt"
openssl verify -CAfile runtime/tls/ca.crt -purpose sslserver \
  -verify_hostname localhost "$SHIFR_CERT_WORK/server.crt"
openssl x509 -in "$SHIFR_CERT_WORK/server.crt" -noout -dates -ext subjectAltName
```

Обе команды `openssl verify` должны вернуть `OK`. Каталоги подготовки и резервной
копии содержат секреты; не прикладывайте их к тикетам. Запишите их пути для отката.

### 6.2. Установка и применение

Убедитесь, что UID/GID владельца совпадают с `LOCAL_UID`/`LOCAL_GID` (раздел 8).
Следующий блок задаёт origins штатной установки; если ранее добавляли свои DNS
или origins для разработки, согласуйте и сохраните их отдельно.

```bash
sudo docker compose stop web api
install -m 0600 "$SHIFR_CERT_WORK/server.key" runtime/tls/server.key
install -m 0600 "$SHIFR_CERT_WORK/server.crt" runtime/tls/server.crt
sed -i \
  -e "s|^LAN_IP=.*|LAN_IP=${SHIFR_IP}|" \
  -e "s|^ALLOWED_ORIGINS=.*|ALLOWED_ORIGINS=https://${SHIFR_IP}:3000,https://${SHIFR_IP}:8443,https://localhost:3000,https://127.0.0.1:3000,https://localhost:8443,https://127.0.0.1:8443|" \
  .env
sudo docker compose up -d --force-recreate --wait --wait-timeout 180 api web
```

Пересоздание нужно для применения `.env` и привязки порта. Один `restart`
не обновит окружение контейнера. Оба TLS-процесса должны загрузить новую пару.

### 6.3. Проверка результата

```bash
sudo docker compose ps
curl --fail --silent --show-error --cacert runtime/tls/ca.crt \
  "https://${SHIFR_IP}:8443/health/frontend"
curl --fail --silent --show-error --cacert runtime/tls/ca.crt \
  "https://${SHIFR_IP}:8443/health/ready"
openssl s_client -connect "${SHIFR_IP}:8443" \
  -CAfile runtime/tls/ca.crt -verify_ip "$SHIFR_IP" \
  -verify_return_error </dev/null
```

Ожидаются healthy для сервисов, `{"status":"ok"}` от frontend и
`{"status":"ok","irc":true}` от API; у `s_client` — успешная проверка цепочки
и IP. Повторите проверку в браузере другого LAN-устройства с установленным CA.
`curl --cacert` проверяет явный файл CA и не доказывает, что браузер уже доверяет ему.
Не используйте `curl -k` как проверку готовности.

### 6.4. Откат

Если установка новой пары не прошла, восстановите предыдущую согласованную пару
и конфигурацию. Используйте путь резервной копии из шага 6.1:

```bash
sudo docker compose stop web api
cp -p "$SHIFR_CERT_BACKUP/env" .env
cp -p "$SHIFR_CERT_BACKUP/server.crt" runtime/tls/server.crt
cp -p "$SHIFR_CERT_BACKUP/server.key" runtime/tls/server.key
sudo docker compose up -d --force-recreate --wait --wait-timeout 180 api web
```

Откат возможен, только если старый сертификат ещё действителен, не скомпрометирован
и прежний IP по-прежнему назначен серверу. После смены сети откат `.env` сам по себе
не вернёт адрес интерфейсу. После успешной приёмки перенесите резервную копию
в защищённое хранилище и удалите лишние копии ключей по принятой политике хранения.

## 7. Контроль срока действия

Настройте ежедневную проверку и уведомление SRE при сроке меньше 30 дней:

```bash
openssl x509 -in runtime/tls/server.crt -checkend 2592000 -noout
openssl x509 -in runtime/tls/ca.crt -checkend 2592000 -noout
```

Ненулевой код означает истечение в пределах интервала либо ошибку чтения/разбора —
оба результата требуют внимания. Для CA начните плановую ротацию значительно
раньше (например, за год), чтобы успеть развернуть доверие на всех устройствах.
Проверяйте и сертификат на сетевом endpoint: файл на диске может уже отличаться
от пары, которую загрузил работающий процесс.

## 8. Диагностика

| Симптом | Проверка и действие |
| --- | --- |
| `cannot assign requested address` при старте web | `ip -4 addr show`; указанный `LAN_IP` отсутствует на хосте. Назначить согласованный адрес либо выполнить раздел 6 с новым IP |
| `ERR_CERT_AUTHORITY_INVALID` / unknown issuer | Проверить CA в хранилище именно используемого браузера и его fingerprint; установка leaf `server.crt` вместо CA не подходит |
| Ошибка имени/IP сертификата | Сравнить URL с `openssl x509 -in runtime/tls/server.crt -noout -ext subjectAltName`; перевыпустить с нужным SAN |
| Сертификат просрочен / ещё не действует | Проверить системное время сервера и клиента, затем `-dates` для CA и server |
| Статика открывается, `/api` возвращает 502 | Проверить журнал web/API, CA и `DNS:localhost` в серверном сертификате |
| TLS работает, API возвращает 403 | Проверить LAN-доступ и `ALLOWED_ORIGINS`; origin включает `https://`, адрес и порт `8443` |
| `Permission denied` на `irc-connect.conf`, TLS или SQLite | Проверить владельцев и числовые UID/GID, а не открывать права всем |

Для диагностики из `project_back`:

```bash
sudo docker compose ps
sudo docker compose logs --tail=80 inspircd api web
ls -ldn runtime runtime/tls runtime/ca data
ls -ln runtime/irc-connect.conf runtime/tls/server.crt runtime/tls/server.key
awk -F= '$1 == "LOCAL_UID" || $1 == "LOCAL_GID" || $1 == "LAN_IP" { print }' .env
```

Не публикуйте полный `.env` или вывод `docker compose config`: они содержат секреты.
Перед передачей журналов проверьте отсутствие чувствительных данных.

### Исправление владельцев после первого запуска через sudo

Только для стандартного Docker Engine без user namespace remapping и только
из обычной учётной записи, которая должна владеть проектом:

```bash
sudo docker compose down
sudo chown -R "$(id -u):$(id -g)" runtime data .env
chmod 700 runtime runtime/tls runtime/ca data
chmod 600 .env runtime/irc-connect.conf runtime/tls/server.key runtime/ca/ca.key
sed -i "s/^LOCAL_UID=.*/LOCAL_UID=$(id -u)/; s/^LOCAL_GID=.*/LOCAL_GID=$(id -g)/" .env
sudo docker compose up -d --wait --wait-timeout 180
```

Это прерывает подключения; каталог данных сохраняется. При rootless Docker,
user namespace remapping, SELinux или нестандартных ACL отдельно проверьте
отображение UID и политику доступа. Не применяйте `chmod 777` и не делайте ключи
общедоступными ради обхода ошибки.

## 9. Замена CA и компрометация ключей

Автоматической ротации, CRL/OCSP и доставки доверия в проекте нет.
Не запускайте setup повторно поверх действующей установки.

При плановой замене CA подготовьте новую пару CA отдельно от рабочих файлов,
разверните новый публичный CA на клиентах, выпустите серверную пару с прежними
SAN и в окно обслуживания замените CA/серверную пару на сервере. Nginx также
проверяет API, поэтому его доверие и сертификат API должны быть согласованы.
Пересоздайте API и web, выполните приёмку, затем удалите старый CA из клиентских
хранилищ. Для такого изменения нужен отдельный план миграции и отката.

При утечке `server.key` изолируйте источник утечки и выпустите новую серверную
пару. Одна замена на сервере не отзывает старый сертификат на клиентах: без
механизма отзыва он остаётся доверенным до истечения. Для немедленного устранения
доверия потребуется заменить CA и удалить старый CA на устройствах.

При утечке `ca.key` старый CA больше нельзя считать доверенным. Создайте новый CA
и серверную пару, доставьте новый CA проверенным каналом, удалите старый со всех
устройств. Откат на скомпрометированную пару недопустим.

Храните резервные копии CA и ключей в защищённом хранилище с ограниченным доступом.
Ключ CA нужен для выпуска, но не для штатной работы контейнеров; его можно хранить
офлайн и предоставлять только на время подписания. Потеря ключа CA потребует
создать новый CA и заново развернуть доверие на устройствах.

## 10. Критерии завершения выдачи

- Fingerprint CA проверен, доверие установлено на целевом устройстве.
- URL совпадает с SAN, IP принадлежит хосту, время на устройствах корректно.
- Nginx и API healthy, HTTPS-проверки проходят без отключения проверки TLS.
- В браузере нет предупреждения; вход и обмен сообщениями работают.
- Зафиксированы срок действия, ответственный и дата следующего продления.
- Клиент получил только публичный CA; ключи остались в защищённом хранении.
