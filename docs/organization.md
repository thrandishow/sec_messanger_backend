# Организация: первый запуск и эксплуатация

## Возможности и роли

| Действие | Сотрудник | Модератор | Администратор |
| --- | --- | --- | --- |
| Общий чат и личные сообщения | Да | Да | Да |
| Чат и история своего отдела | Да | Да | Да |
| Чаты и история других отделов | Нет | Нет | Да |
| Читать объявления и полезные ресурсы | Да | Да | Да |
| Публиковать объявления, добавлять/удалять ресурсы | Нет | Да | Да |
| Создавать аккаунты, менять роли, блокировать, сбрасывать пароль | Нет | Нет | Да |
| Создавать отделы и назначать сотрудников | Нет | Нет | Да |
| Смотреть журнал аудита | Нет | Нет | Да |

Личные сообщения и вложения доступны только двум участникам: роль администратора
не открывает чужие личные диалоги через API. Администратор хоста с доступом к SQLite
может читать данные на диске: сквозного шифрования нет.

Один сотрудник состоит максимум в одном отделе. Членство управляет доступом ко
всей истории отдела, включая сообщения до назначения. После смены отдела доступ
к прежней истории и файлам прекращается. История общего чата доступна всем аккаунтам.
Старые аккаунты при обновлении становятся сотрудниками без отдела; первый
администратор не выбирается автоматически. Существующие аккаунты и сессии сохраняются.

## Обновление существующей установки

Остановите API и web, сделайте защищённую резервную копию всего `data/`, затем
обновите **обе** папки репозиториев. Не удаляйте `.env`, `runtime/` и `data/`.
Из `project_back` выполните:

```bash
sudo docker compose up --build -d --wait --wait-timeout 180
```

Схема SQLite обновляется при старте API добавлением колонок и таблиц.
Сообщения из старой версии, существовавшие только в памяти браузеров, восстановить
нельзя. Новая история начинается с момента обновления.

Публичная регистрация закрыта. Старый `REGISTRATION_TOKEN` больше не используется,
его можно удалить из `.env`. Уже созданные аккаунты продолжают входить с прежними паролями.

## Первый администратор

Все команды ниже — из `project_back`. Для новой установки сначала выполните
`bash start.sh <LAN-IP>` (или `sudo bash start.sh <LAN-IP>`, если Docker требует sudo).
Скрипт учитывает UID/GID пользователя, вызвавшего sudo. Владелец проекта должен
иметь право записи; прямой первый запуск из root-shell не поддерживается.

**Если нужный аккаунт уже существует**, один раз назначьте его администратором:

```bash
sudo docker compose run --rm --no-deps -T api node dist/admin.js --promote alice
```

Замените `alice` на существующий ник. Сессии этого пользователя отзываются — войдите
в веб-интерфейс заново. Команда работает только при отсутствии активного администратора.

**Для новой базы** создайте администратора, введя пароль скрыто в Bash:

```bash
sudo -v
read -r -s -p 'Пароль администратора (12–128 символов): ' SHIFR_ADMIN_PASSWORD
printf '\n'
printf '%s\n' "$SHIFR_ADMIN_PASSWORD" | sudo docker compose run --rm --no-deps -T api node dist/admin.js --nickname admin
unset SHIFR_ADMIN_PASSWORD
```

Пароль передаётся через stdin; его не нужно помещать в команду, `.env`, логи или
Git. `sudo -v` запрашивает системный пароль до конвейера. На сервере с уже существующим
администратором bootstrap откажет: дальнейшие аккаунты создаются в админ-панели.

Откройте `https://<LAN-IP>:8443`, войдите и выберите **«Управление и аудит»**:

1. Во вкладке «Отделы» создайте отдел, например «Бухгалтерия», адрес чата `accounting`.
2. Во вкладке «Сотрудники» создайте аккаунты, назначьте роли и отделы.
3. Передайте каждому сотруднику его пароль доверенным каналом.
4. Для официальных публикаций назначьте модератора. Он сможет писать в «Объявления»
   и загружать шаблоны/графики в «Полезные ресурсы».

Изменение роли, отдела, пароля или активности отзывает все сессии пользователя и
закрывает его WebSocket. Нельзя отключить или понизить последнего активного
администратора. Сброс пароля выполняется в форме изменения сотрудника; пустое поле
сохраняет старый пароль. Самостоятельного восстановления пароля и принудительной
смены временного пароля в текущей версии нет.

## Сообщения и документы

InspIRCd подтверждает отправку серверным эхом. Только после этого API записывает
сообщение в SQLite и передаёт сохранённое событие браузерам. ID одинаковый в истории
и WebSocket; получатели не создают дополнительные записи. Это подтверждение
сохранения на сервере, а не прочтения адресатом. При ошибке сохранения UI получает ошибку.

История загружается страницами по 50 сообщений. Кнопка «Более ранние сообщения»
загружает следующую страницу; обновление вкладки историю не удаляет. Для отправки
личного сообщения адресат должен быть онлайн; очередь офлайн-доставки не реализована.
Если соединение отправителя оборвалось до получения IRC-эха, подтверждение и
сохранение не гарантированы — после восстановления проверьте историю перед повтором.

Скрепка прикрепляет документ к сообщению. Максимум — **10 МиБ на файл**, суммарная
квота содержимого файлов — **1 ГиБ**. Файлы хранятся как BLOB в SQLite. Неприкреплённые
загрузки старше суток очищаются при следующей загрузке. При заполнении квоты API
возвращает `507 STORAGE_FULL`; автоматического удаления истории и прикреплённых
файлов нет. Удаление ресурса освобождает его логическую квоту; размер файла SQLite
может не уменьшиться, освобождённые страницы переиспользуются.

Файлы всегда скачиваются как вложения с `application/octet-stream`; просмотр HTML,
SVG и других активных форматов на origin приложения запрещён. Антивирусной проверки
в MVP нет — открывайте документы согласно правилам вашей организации.

## Аудит и резервные копии

Вкладка «Аудит» доступна администраторам. Записываются успешные и неудачные входы,
выходы, создание/изменение аккаунтов (включая предыдущие и новые роли/отделы),
создание отделов, загрузки/скачивания файлов и удаление ресурсов. События содержат
UTC-время, идентификатор участника, действие, объект и IP клиента. Пароли, cookie и
тексты сообщений в аудит не записываются.

Аудит хранится в таблице `audit` той же SQLite. Это журнал приложения, **не
неизменяемое хранилище**: администратор хоста может изменить файл БД. Для требований
неизменяемости нужен отдельный защищённый приёмник внутри LAN.

`data/` содержит аккаунты, сессии, историю, документы и аудит. Чтобы получить
согласованную резервную копию, остановите `web` и `api`, скопируйте весь каталог
`data/` (включая WAL/SHM при их наличии), затем запустите сервисы:

```bash
sudo docker compose stop web api
# Скопируйте data/ в защищённое резервное хранилище по правилам организации.
sudo docker compose up -d --wait api web
```

Отдельно защищённо храните `.env` и `runtime/`; закрытые ключи не отправляйте
пользователям. Политика срока хранения истории и аудита задаётся организацией;
автоматическая ротация пока отсутствует. SQLite и соединения IRC рассчитаны на
**один экземпляр API**, горизонтальное масштабирование не поддерживается.

## Пакет для изолированной сети

На машине с интернетом и Docker, **той же архитектуры, что целевой сервер**, выполните
из настроенного `project_back` (папка `project_front` рядом):

```bash
bash scripts/export-offline.sh /absolute/path/to/shifr-offline
```

Если Docker требует sudo, запустите эту команду через sudo. Скрипт собирает четыре
образа, сохраняет `images.tar` и SHA-256, Compose, инструкции и автономный `start.sh`.
В пакет **не включаются** текущие аккаунты, базы, ключи и `.env`. Перенесите весь
каталог пакета доверенным способом. На целевом Linux заранее должны быть установлены
Docker Engine и Compose v2; Node.js, npm, Git и OpenSSL на хосте не требуются.

Из каталога пакета на изолированном сервере:

```bash
sudo bash start.sh 192.168.1.10
```

Адрес замените на IP сервера. На первом запуске проверяется checksum архива,
загружаются локальные образы и создаётся новая конфигурация. Наличие всех образов проверяется перед настройкой. Для `up` используются
`--no-build --pull never`, для `run` — `--pull never`: запускающий скрипт
не обращается к реестрам образов или npm.
Повторный запуск — `sudo bash start.sh`.

После запуска создайте первого администратора командами выше и установите
`runtime/tls/ca.crt` на клиентах по [инструкции SRE](certificates-sre.md).
При смене IP следуйте разделу перевыпуска сертификата, а не повторной настройке.
Для обновления действующего офлайн-сервера загрузите новый `images.tar` через
`docker load -i images.tar`, обновите Compose и выполните
`docker compose up -d --no-build --pull never --wait` после резервного копирования.

Compose публикует только Nginx на LAN-IP:8443; API/IRC доступны лишь внутри Docker.
Соблюдайте firewall LAN и не публикуйте этот порт в интернет. Наличие отдельной
сети Docker не заменяет физическую/сетевую изоляцию стенда.
